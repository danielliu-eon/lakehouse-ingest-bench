# Publishing a result

A result is one `run.json` (`schema_version: 2`) under `results/<engine>/`,
plus `RESULTS.md` regenerated from every file here. Both arrive together, from
`scripts/finish.sh <run_id> --publish results/` — never by hand-editing either.
`finish.sh` refuses to publish a run whose `run_valid` is false unless you pass
`--publish-invalid`, which keeps the run but never as a headline.

## The rules (spec §11.2, enforced by `scripts/validate-results.py`)

- Every run measured a **fresh table and topic** — no result reuses either
  across runs.
- `run_valid: true`, or the result is kept with its validity state shown in
  `RESULTS.md`'s row (`producer_bound`, `void`, `undersized`, `not drained`)
  and never presented as a headline number.
- The fleet, its machine types and the prices behind the cost column are
  disclosed — never a redacted or approximate fleet.
- Any engine tuning beyond the run-spec's own knobs is a **separately named
  variant**, not a silent re-run of the same file.
- No result comes from a shortened (`producer.seconds` set) or overridden
  (`--set`) corpus. A probe run is not a result.
- A `producer_bound` run voids the cell — the offer, not the engine, was the
  bottleneck, and the run says nothing about the engine.
- An external result carries `run.engine_versions` as `{name, version, notes}`
  — what its operator said, since the harness never ran it.
- No company, product, person, account id, bucket, cluster, node-pool or
  taint name anywhere in a published file.

`RESULTS.md` is generated by `results-table` and is never hand edited; a
`results-table results/ --out results/RESULTS.md` that changes nothing is what
"fresh" means for CI.
